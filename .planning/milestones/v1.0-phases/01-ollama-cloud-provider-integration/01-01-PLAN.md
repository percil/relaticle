## D-06 model tags: corrected against the live endpoint, decision substance unchanged

**What D-06 says:** the first two catalog rows are `gpt-oss:20b-cloud` and `gpt-oss:120b-cloud`.
**What the endpoint serves:** `gpt-oss:20b` and `gpt-oss:120b`. There is no `-cloud` suffix.

Evidence, `GET https://ollama.com/v1/models` run 2026-09-02 (the endpoint is public, so this is
reproducible without a key):

```
{"object":"list","data":[
  {"id":"gpt-oss:20b","object":"model","created":1754352000,"owned_by":"ollama"},
  {"id":"gpt-oss:120b","object":"model","created":1754352000,"owned_by":"ollama"},
  ...19 rows total, none carrying a -cloud suffix
]}
```

**Why the research said otherwise.** Pitfall 2 and the `-cloud` convention are real, but they
describe addressing a cloud-hosted model *through a local Ollama instance*, which proxies to the
cloud and disambiguates with the suffix. This integration points the driver straight at
`https://ollama.com`, where the bare tag is the address. The two situations were conflated. Note
that `.planning/research/STACK.md` line 23 already recorded the live `/api/tags` catalog with bare
names while `PITFALLS.md` described the suffixed form; the conflict was present in the research and
is resolved here by observation.

**What changes:** the tag literals only. D-06's substance is untouched: the same two models, the
small one to prove the path cheaply and the large one to answer the 120 second latency question,
both starting `auto: false` per D-03. No model was substituted, dropped, or deferred.

**What does not change:** the risk Pitfall 2 protects against. A tag that is not in the listing
still fails at inference, `ModelProbe` still catches it at save time, and the picker still exists so
tags are chosen rather than typed. Nothing in the pipeline may strip, add, or normalize a suffix.

**Flag for the user:** this correction is surfaced rather than applied silently, because it
contradicts a locked decision's literal text. Confirm the tags before plan 02 saves them.

<assumption_delta_decision>
**Detector:** `detected: true` (signal: `chosen`/"selectable", from the ROADMAP success criterion
"an operator sees Ollama Cloud as a selectable provider").

**Noun under pressure:** the AI provider named `ollama`. This phase introduces a second Ollama,
which is the classic singular-to-plural seam where the original abstraction should normally be
promoted to the general case and the old one demoted to one variant of it.

**Decision: `add-alongside` (no promotion).**

**Rationale (already locked, not re-litigated):** CONTEXT.md `<domain>` states the phase boundary
explicitly as a distinct `ollama_cloud` config entry "never touching the existing self-hosted
`ollama` entry", and REQUIREMENTS.md lists "Folding Ollama Cloud into the existing self-hosted
`ollama` config entry" in the Out of Scope table. Promotion is not merely unnecessary here, it is
the failure mode: the two entries are not two instances of one concept. The self-hosted entry is
deliberately free, unmanaged, never `ModelProbe`-verified, and excluded from plan gating
(`ModelRegistry::ollamaFromEnv()` hardcodes `min_plan: free`, `self_hosted: true`). Generalizing
them into one noun would drag paid cloud models into that trust boundary, which is Pitfall 1.

**Residual coupling this decision does not remove (see Task 2):** the two providers share a
`laravel/ai` driver, so they are already fused at the `Lab::Ollama` layer whether or not the config
keys stay separate. That fusion is what Task 2 has to resolve, and it is the one place where
"add-alongside" does not buy full separation.
</assumption_delta_decision>

D-01 asked for `parallel_tool_calls: false` to be wired for Ollama Cloud before the first probe, so
the catalog can earn the stronger `api` write guard, with an explicit fallback to `prompt` plus
documentation if the provider does not honor it. Source reading has surfaced two facts that decide
which branch is taken, so establish them first and then take the branch D-01 already chose.

FACT 1, the two call sites disagree by construction. In a real turn the Ollama gateway calls
`providerOptions($provider->driver())`, and the driver for this config block is the string
`ollama`, which `TextGenerationOptions` converts to `Lab::Ollama`. `ModelProbe::writeGuardFor()`
instead passes the app config key `ollama_cloud`. So an arm keyed on `Lab::Ollama->value` is read
by real turns but not by the probe, and an arm keyed on `ollama_cloud` is read by the probe but
never by a real turn. The second shape is the dangerous one: it would record `write_guard: api`
while transmitting nothing.

FACT 2, the driver has nowhere to put the option. The Ollama gateway hoists only `format`,
`keep_alive`, `think`, `logprobs`, and `top_logprobs` to the request top level and merges every
other key into the `options` bag of a native `POST api/chat` request. `parallel_tool_calls` is an
OpenAI chat-completions parameter, not an Ollama runtime option, so it would arrive nested inside
`options` on an endpoint that has no such parameter.

`POST https://ollama.com/api/chat` for `gpt-oss:20b` with a trivial message, once with an

status codes and whether the option is echoed or rejected. Also note whether an unknown key inside
`options` produces an error, since that alone would make the arm unsafe regardless of the guard.
