<objective>
Add the missing `reverb` service to the self-hoster-facing production `compose.yml`, following the `horizon` and `scheduler` sidecar pattern already established in that file, and wire the two Reverb address families onto the existing services.

Purpose: `laravel/reverb` is the app's default broadcaster and chat streaming runs entirely through it, yet no compose file has ever declared a Reverb daemon. Nobody who follows the published quick start gets working real-time chat. This plan closes that for the published image (D-02: self-hoster scope; Relaticle's own Forge deployment is explicitly out of scope and `deploy.yml` is not touched).

Output: a `reverb` service in `compose.yml`, the `BROADCAST_REVERB_*` and client-facing `REVERB_*` environment wiring on the existing services, and a test case pinning the compose contract so the addressing split cannot silently regress.
</objective>

    The `reverb` service copies the `horizon` shape with these deltas:
    - `image: ghcr.io/relaticle/relaticle:latest`, `restart: unless-stopped`, `stop_signal: SIGTERM`, matching its siblings.
    - `command: ["php", "/var/www/html/artisan", "reverb:start", "--host=0.0.0.0", "--port=8080"]`.
    - `ports: - "${REVERB_PORT:-8080}:8080"`. This must be published: without it the browser has no socket to open, and the whole point of the published compose file is that `docker compose up -d` works. Note in a comment that a self-hoster terminating TLS should front this port with their reverse proxy and set `REVERB_SCHEME=https` accordingly.
    - `environment:` carries `APP_KEY: ${APP_KEY:?APP_KEY is required}`, `APP_ENV: ${APP_ENV:-production}`, `APP_DEBUG: ${APP_DEBUG:-false}`, `APP_URL: ${APP_URL:-http://localhost}`, `LOG_CHANNEL: ${LOG_CHANNEL:-stderr}`, `REVERB_APP_ID: ${REVERB_APP_ID:?REVERB_APP_ID is required}`, `REVERB_APP_KEY: ${REVERB_APP_KEY:?REVERB_APP_KEY is required}`, `REVERB_APP_SECRET: ${REVERB_APP_SECRET:?REVERB_APP_SECRET is required}`, `REVERB_ALLOWED_ORIGIN_EXTRA: ${REVERB_ALLOWED_ORIGIN_EXTRA:-}`, `REDIS_HOST: redis`, `REDIS_PASSWORD: ${REDIS_PASSWORD:-null}`, `REDIS_PORT: 6379`, and `AUTORUN_ENABLED: "false"`.
    - `APP_URL` is load-bearing here, not boilerplate: Reverb builds `allowed_origins` from `config('app.url')` inside this container, so a missing or wrong value closes every browser handshake with code 4009. `REVERB_ALLOWED_ORIGIN_EXTRA` is the documented escape hatch for a self-hoster whose WebSocket origin differs from `APP_URL`.
    - Omit the `DB_*` keys entirely. Reverb does not touch Postgres, and copying horizon's database block would be cargo cult. Omit the `storage:` volume for the same reason.
    - `depends_on: redis: condition: service_healthy`. Do not depend on `app` being healthy: Reverb has no reason to wait for the web container, and adding the edge only slows cold starts.
    - `healthcheck: test: ["CMD", "healthcheck-reverb"]` with `start_period: 10s`, mirroring `healthcheck-horizon` and `healthcheck-schedule`. That binary is cited from the vendor's Reverb guide but was never verified against this pinned image tag (RESEARCH.md assumption A4). Probe it first with the command in verify; if it is absent, fall back to a TCP check against port 8080 using a tool the image actually ships, and leave a one-line comment recording which branch was taken and why.

    On the existing `app`, `horizon` and `scheduler` services, add the server-to-server family to each `environment:` block: `BROADCAST_REVERB_HOST: reverb`, `BROADCAST_REVERB_PORT: 8080`, `BROADCAST_REVERB_SCHEME: http`. The explicit scheme is mandatory. `config/broadcasting.php` only downgrades to http for the literal hosts 127.0.0.1, ::1 and localhost, and `reverb` is not one of them, so leaving the scheme unset makes the app attempt TLS against a container that speaks plain HTTP and every broadcast fails with no user-visible error. Add a short comment above the three keys saying so, so a future reader does not "simplify" them away.

    On the `app` service only, add the client-facing family: `BROADCAST_CONNECTION: ${BROADCAST_CONNECTION:-reverb}`, `REVERB_APP_KEY: ${REVERB_APP_KEY:?REVERB_APP_KEY is required}`, `REVERB_HOST: ${REVERB_HOST:-localhost}`, `REVERB_PORT: ${REVERB_PORT:-8080}`, `REVERB_SCHEME: ${REVERB_SCHEME:-http}`. These are what the panel renders into the page for the browser after plan 02-01, so they must be present on the container that serves HTML. Add a comment marking them as the browser-facing address, distinct from the `BROADCAST_REVERB_*` block directly above.

    Leave `postgres: image: postgres:17-alpine` exactly as it is. D-04 is already satisfied on this side of the phase; the verify step confirms it did not drift.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet to published reverb port | The reverb container publishes a host port so a browser can open the socket directly or through a proxy |
| container to container on the compose network | app, horizon and scheduler push broadcasts to reverb over plain HTTP |
| self-hoster environment to compose | Reverb credentials arrive as environment variables from the operator's own `.env` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-06 | Denial of Service | The published reverb host port reachable from the internet without a proxy | medium | accept | Reverb ships connection and message limits already exposed as `REVERB_APP_MAX_CONNECTIONS`, `REVERB_APP_MAX_MESSAGE_SIZE` and `REVERB_APP_RATE_LIMITING_ENABLED` in `config/reverb.php`. Publishing the port is required for the documented quick start to work at all; the reverse-proxy path documented in plan 02-03 is the hardened option. |
| T-02-07 | Spoofing | A client connecting from an unexpected origin | medium | mitigate | `config/reverb.php` derives `allowed_origins` from `config('app.url')`, so the reverb service is given `APP_URL` explicitly in Task 1. `REVERB_ALLOWED_ORIGIN_EXTRA` is wired as the single documented escape hatch rather than allowing a wildcard. |
| T-02-08 | Information Disclosure | `REVERB_APP_SECRET` present in the reverb container's environment | low | accept | The secret is required by the daemon to authenticate server-side pushes and never leaves the container. It is guarded with `${REVERB_APP_SECRET:?REVERB_APP_SECRET is required}` so the stack refuses to start on a placeholder. |
| T-02-09 | Tampering | Broadcast payloads pushed over plain HTTP between containers | medium | accept | Same rationale as T-02-04 in plan 02-01: the traffic stays on the private compose network, and `BROADCAST_REVERB_VERIFY` remains available for anyone who does terminate TLS in front of Reverb. |
| T-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not triggered: this plan installs no packages and introduces no new base image. It reuses `ghcr.io/relaticle/relaticle:latest`, already published by this repository's own `docker-publish.yml`. |
</threat_model>
