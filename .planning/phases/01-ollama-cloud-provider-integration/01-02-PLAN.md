  <decision>The credit_multiplier for gpt-oss:20b and gpt-oss:120b on this install</decision>
  <context>
D-05 left this open on purpose: it is the only honest cost signal for these rows, because D-04 sets
`input_per_mtok` and `output_per_mtok` to null (Ollama Cloud bills a subscription credit pool, not
per token). The multiplier is what each workspace is actually charged per turn, so it is a pricing
decision rather than an implementation detail, and D-05 explicitly asks for a proposal confirmed by
the user rather than a value picked silently.

The existing catalog uses three bands, visible in `packages/Chat/config/chat.php`: 1.0 for
free-tier-eligible models, 1.5 for pro-tier models, and 3.0 for the most expensive model on offer.
Ollama Cloud is a flat 20 dollars a month on the Pro tier (D-02), so marginal cost per turn is near
zero once the subscription is paid, and the multiplier is really a rationing dial for the weekly
quota rather than a cost passthrough.

Changing a multiplier later is cheap: it is a panel edit with no deploy and no migration, and
historical `ai_credit_transactions` rows store the credits already charged rather than recomputing
from the multiplier. So this decision is reversible; it is gated because it is the user's to make,
not because it is expensive to undo.

This checkpoint carries `blocking-human` because auto-selecting a default price for a paying
customer's workspaces is exactly the outcome the gate exists to prevent.
  </context>

STEP A, clear the config cache first. A `config/ai.php` cached before plan 01's deploy makes
`verified()` reject every save with a message about no API key being configured for the provider,
even when `.env` is correct. Run `php artisan config:clear`, then confirm
`php artisan config:show ai.providers.ollama_cloud` shows the key present and the url as the bare
host with no path segment.

STEP B, open the sysadmin AI settings page. Derive the panel URL from the running app rather than
assuming it, per the agent-browser skill. Use the Refresh model lists header action once so the
`ollama_cloud` listing is fetched fresh rather than served from a stale 24-hour cache.

STEP C, add the first row. Add a model, choose Ollama Cloud as the provider, and confirm the model
Select now offers a real list of published tags rather than an empty dropdown. That
observation is the live confirmation of OLLAMA-03 and it is worth recording verbatim: note how many
tags the list held and whether `gpt-oss:20b` and `gpt-oss:120b` were both present.
Select `gpt-oss:20b` from the list. Do not type it. The whole point of the listing arm is that
a tag is picked, never keyed, so no character of it can be lost to a typo. Note that plan 01's
`<tag_correction>` block established these tags carry no `-cloud` suffix when addressing
`https://ollama.com` directly; take whatever the list offers rather than what D-06's literal text
says, and do not append a suffix to make it match.

Open the row's configure modal and set `min_plan` and `credit_multiplier` to the values the decision
checkpoint above settled. Leave both per-mtok fields empty so they persist as null, per D-04. Leave
the Auto toggle off, per D-03, uniformly and regardless of model size. Leave the Enabled toggle on.

STEP D, add the second row the same way for `gpt-oss:120b`, with its own decided `min_plan`
and `credit_multiplier`, Auto off, Enabled on, per-mtok fields empty.

STEP E, save and read the result. Saving probes every unmeasured pairing against a real request
carrying the full CrmAssistant tool surface. Two outcomes are meaningful and both must be recorded:

If the save is rejected, the notification carries the provider's own sentence. Record it verbatim.
A rejection naming a missing or unknown model is the tag-fidelity failure mode from Pitfall 2 and
means a tag was keyed rather than picked, or a suffix was added to match D-06's literal text. A rejection about the request body is a driver-level
problem and is a blocker for the phase, not a retry.

If the save succeeds, both rows show the Verified badge. Hover each badge and record the tooltip
verbatim: it states the measured tool support and the measured write guard. That `write_guard` value
is the one this catalog inherits forever, because a pass is cached and never re-checked. Compare it
against the branch plan 01 took and state in the SUMMARY whether they agree. If plan 01 took the
fallback branch, the expected value is the weaker prompt guard and it is consciously accepted, with
the `PendingAction` approval gate remaining the enforcing mechanism. If they disagree, that is the
probe-versus-transport mismatch plan 01 flagged and it is a blocker, not a discrepancy to note and
move past.

STEP F, confirm the plan boundary is real, not assumed. With both rows saved, check that the model
whose `min_plan` is pro is absent from the chat model picker for a free-plan workspace and present
for a pro-plan workspace, and that the free-floor model appears for both. Use the existing local
seed data for the two workspace plans rather than editing a team record by hand.

STEP G, read the health dashboard. Only a servable row registers a check, and `isServable()` needs
the measurement STEP E just wrote, so this is the first moment the provider check exists at all.
Confirm a check named for the ollama_cloud chat provider is present and record its status and its
short summary. Green is the expected outcome. A warning naming a rate limit or an unreachable
provider is transient and should be re-run once. A failure naming an unhandled provider case means
plan 01's arm is not being reached and is a blocker. A failure naming an unavailable model means the
health path resolves to a URL Ollama does not serve, which is assumption A-01 from plan 01 coming
back, and is likewise a blocker.

Note that `reachableModels()` registers one check per provider, preferring the entry available on
every plan, so exactly one of the two rows will be the watched model. Record which one.

STEP H, read the stored result back from the command line rather than from the form you just filled
in. Run `php artisan chat:models` and copy the two ollama_cloud rows into the SUMMARY. Its table
prints the registry as the app resolves it, including the measured tools and write_guard columns, so
it is the independent confirmation that the panel wrote what it displayed.
