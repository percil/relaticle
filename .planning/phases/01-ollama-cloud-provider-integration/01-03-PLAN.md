  <action>
Two measurements, both of which need the real queue. Do not run either against a sync queue: a sync
turn does not go through Horizon, does not hit the job timeout, and cannot be made concurrent, so it
would answer neither question.

MEASUREMENT A, latency against the 120 second ceiling. Send one chat turn on `gpt-oss:120b`
that genuinely requires several sequential tool round-trips inside a single job, not a single
lookup. A request that reads some CRM records and then proposes a write against what it read is the
right shape, because each round-trip is another model call inside the same 120 second budget. Record
the wall time from dispatch to the turn settling, and record how many tool calls the turn made.

Compare against 120 seconds and say plainly which of three states holds: comfortably under, close
enough that a slower day would exceed it, or over. The failure mode when it exceeds is already
handled, the user sees a message about the model not responding in time and the reservation settles
at minimum, but that is degraded-and-handled rather than success, and Pitfall 6 expects it to fire
measurably more often here than on the commercial providers.

Also run the same shaped request on `gpt-oss:20b` and record its wall time, so the SUMMARY
carries a small-versus-large comparison rather than a single number with nothing to read it against.

MEASUREMENT B, the concurrency ceiling. D-02 records the working assumption that this deployment is
on the Pro tier with roughly three concurrent requests, sourced from third parties because Ollama
publishes no official figure, and asks for it to be confirmed against the live account. Start
concurrent chat turns on Ollama Cloud models, beginning at two and increasing, until either a turn is
rejected or you have clearly exceeded the assumed ceiling without one. Record the number at which
behavior changed, or record that it did not change through the range tested.

If a rejection occurs, its shape is the point, not its existence. Capture the exception class and the
HTTP status. Then check that against `isRateLimited()`, which recognizes a typed rate-limited
exception, a typed overloaded exception, and a `RequestException` carrying status 429, 529, or 503,
and nothing else. A concurrency rejection arriving as, for example, a 400 with an explanatory body
would fall outside all of those, and the user would see the generic assistant-error copy instead of
the being-rate-limited copy, and the job would fail instead of being released for retry. State
explicitly in the SUMMARY whether the observed shape is classified correctly.

Note the structural gap either way: `provider_starts_per_second` is a global per-second start-rate
cap, and Ollama Cloud limits concurrent in-flight requests. A long-running stream holds its slot for
the whole generation, so a start rate well under the cap can still push past a concurrency ceiling.
Do not change that config in this plan. Record whether a per-provider override is worth proposing
as follow-up work, with the measured numbers behind the recommendation.

Do not flip either model's Auto toggle regardless of how well the timings come out. D-03 admits
nothing to the Auto chain in this phase, uniformly and regardless of size. If the timings are good,
say so and recommend it as follow-up work.

Walk these, in order, recording what actually happened at each step:

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| End user to CRM writes | A chat turn on a new provider proposes real record creation, update, and deletion behind the PendingAction approval gate |
| Relaticle app to Ollama Cloud | Concurrent long-lived streams cross this boundary and are the surface where a quota or concurrency rejection appears |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-12 | Elevation of Privilege | Parallel tool calls bypassing sequential approval | high | mitigate | Plan 02 recorded the measured write_guard. When it is the weaker prompt guard, the provider itself does not refuse parallel tool calls and the PendingAction approval gate is the sole enforcement, so steps 5 and 6 of the walkthrough are the load-bearing check: one card per plan, approved once, with dependents cancelling on rejection. A card that hides the link being approved is the exact failure this design exists to prevent. |
| T-01-05 | Denial of Service | Concurrency ceiling versus the per-second start-rate gate | medium | mitigate | Task 1 measures the real ceiling and confirms whether the rejection shape reaches `isRateLimited()`. A misclassified rejection fails the turn instead of releasing it for retry and shows the user the wrong copy, which is a correctness problem, not only a comfort one. |
| T-01-13 | Information Disclosure | Screenshots and transcripts captured during the walkthrough | medium | mitigate | Use local seed data only. <flagged_assumptions>
**A-02 (OLLAMA-06, unclassified from the spec-less edge probe), carried from plan 01.** Whether a
full streaming, tool-calling, propose-and-approve turn behaves correctly on Ollama Cloud cannot be
reduced to an automated assertion in this codebase. `ModelProbe` sends one message through
`ModelProbeAgent`, which forbids tool calls. This plan resolves the assumption by observation and
records the evidence; it does not convert it into a passing test.

**Carried assumption on tool-calling reliability.** Research rated general Ollama tool-calling
reliability at low-to-medium confidence from community sources, not specific to these models. The
walkthrough is the first real evidence for these two tags; a model that streams correctly but calls
tools unreliably would surface at steps 3 through 5, and that outcome is a finding, not a failure of
the plan.
</flagged_assumptions>
